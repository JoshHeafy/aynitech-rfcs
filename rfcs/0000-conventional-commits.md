# Summary

Adopt [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) as the standard format for commit messages and PR titles across all AyniTech R&D repositories (Kriptex and AyniFX). The goal is a readable, searchable history that can later feed automatic changelogs and semantic versioning.

# Motivation

Today each team and each developer writes commits in their own style (`fix`, `arreglos`, `wip`, `cambios en cotizador`). This causes:

- A git history that is hard to scan during code review, incident investigation or `git bisect`.
- No quick way to tell whether a change is a feature, a fix or a refactor without opening the diff.
- Release notes written by hand, from memory, at the end of the sprint.
- No visible signal for breaking changes between services (e.g. a Go API contract change that impacts the Flutter app).

If we do nothing, the history keeps degrading as the team grows and new engineers have no reference for what a "good" commit looks like.

Expected outcome: any engineer can read `git log --oneline` and understand what happened, and tooling can be added later (changelog, versioning) without rewriting history.

# Guide-level explanation

Every commit message follows this shape:

```
<type>(<scope>): <short description>

[optional body]

[optional footer(s)]
```

Example commits:

```
feat(exchange): add rate alert creation endpoint
fix(auth): refresh token not rotated after password change
refactor(payments): move bank adapter to outbound port
docs(rfcs): add conventional commits RFC
chore(deps): bump flutter_bloc to 9.x
```

## Types

| Type | When to use it |
| --- | --- |
| `feat` | A new capability visible to users or consumers of the API |
| `fix` | A bug fix |
| `refactor` | Code change that neither fixes a bug nor adds a feature |
| `perf` | Change that improves performance |
| `test` | Adding or correcting tests |
| `docs` | Documentation only |
| `style` | Formatting, whitespace, no logic change |
| `build` | Build system or dependencies (go.mod, pubspec.yaml, Dockerfile) |
| `ci` | CI/CD configuration and pipelines |
| `chore` | Maintenance tasks that don't fit above |
| `revert` | Reverts a previous commit |

## Scope

Optional but recommended. It names the area touched, in lowercase: `auth`, `exchange`, `payments`, `alerts`, `kyc`, `db`, `infra`, `ui`. Each team can keep its own list of scopes in its repo's README.

## Breaking changes

Add `!` after the type/scope and explain it in the footer:

```
feat(api)!: replace rate endpoint response format

BREAKING CHANGE: `rate` is now an object `{ buy, sell }` instead of a number.
```

## Referencing tickets

Use a footer to link the Linear ticket:

```
fix(alerts): avoid duplicate notification on rate update

Refs: ANI-123
```

## Pull requests

We squash-merge, so the **PR title** must follow the same format. That title becomes the commit on `main`. Individual commits inside a PR branch are encouraged to follow it but are not enforced.

## Rules of thumb

- Description in imperative mood, lowercase, no trailing period, max ~72 characters.
- One logical change per commit.
- Body explains the *why*, not the *what* (the diff already shows the what).

# Reference-level explanation

## Format specification

Follows the Conventional Commits 1.0.0 specification:

- `type` is required and must be one of the types listed above.
- `scope` is optional, wrapped in parentheses.
- `!` before the colon marks a breaking change; `BREAKING CHANGE:` in the footer is equivalent.
- Footers use the git trailer format (`Token: value`).

## Interaction with the stack

- **Go backend (hexagonal):** suggested scopes map to domains and adapters (`exchange`, `payments`, `kyc`, `db`). Moving code between ports/adapters is a `refactor`.
- **Flutter app:** `feat`/`fix` for user-visible changes; `ui` scope for purely visual work.
- **Infra / k8s:** `ci`, `build` or `chore(infra)` depending on the change.
- **Cross-service changes:** if a change breaks a contract, it must use `!` so the consuming team notices it in the log.

## Enforcement (phased)

1. **Phase 1 — Convention only.** Documented here, applied in code review. No tooling required.
2. **Phase 2 — PR title check.** A GitHub Action validates the PR title (e.g. `amannn/action-semantic-pull-request`). Low friction, because it only checks one line per PR.
3. **Phase 3 — Optional local hook.** `commitlint` or `lefthook` for those who want local validation. Not mandatory.

We start at Phase 1; moving to Phase 2 requires a short follow-up decision from the Guild Leads.

## Edge cases

- **Merge commits and reverts generated by git/GitHub:** exempt from validation.
- **Work in progress:** use a draft PR instead of `wip` commits; commits inside the branch are squashed anyway.
- **Multiple changes in one commit:** split them. If impossible, use the most significant type.

## Migration

No history rewrite. The convention applies to new commits from the date the RFC is accepted. Existing repos adopt it progressively.

# Drawbacks

- Small learning curve for people used to free-form messages.
- Slight extra effort per commit, especially choosing a type and scope.
- Without enforcement (Phase 2), adherence depends on discipline and review.
- Disagreements will appear at the edges (`refactor` vs `chore`, `fix` vs `feat`). We accept that the convention is a guide, not a perfect taxonomy.

# Alternatives

- **Free-form messages (status quo):** zero friction, but no structure and no tooling possibilities.
- **Gitmoji:** more visual, but emojis are harder to type, search and parse, and don't map to semantic versioning.
- **Angular commit convention (original):** Conventional Commits is derived from it and is more general; no reason to adopt the stricter parent.
- **Only a PR template, no commit convention:** covers the PR description, but not the history of `main`.

Not doing anything keeps the cost of reading history and preparing releases growing over time.

# Unresolved questions

- Official list of scopes per repo, or leave it free?
- When do we move from Phase 1 to Phase 2 (PR title check in CI)?
- Out of scope: automatic changelog generation and semantic versioning tooling; these can be a follow-up RFC once the convention is adopted.
